### **Section 2: Technical Knowledge (15 minutes)**  

#### **Embedded Security & IoT Protocols**  
**Q3: Can you explain some common security threats in IoT and embedded systems?**  
*A3: Some common threats include firmware vulnerabilities, insecure boot mechanisms, lack of encryption, side-channel attacks, and insecure communication protocols. Attackers often exploit debugging interfaces like JTAG and UART, or use reverse engineering techniques to extract firmware and find vulnerabilities.*  

**Q4: How would you secure an embedded device from unauthorized access?**  
*A4: I would implement a multi-layered approach that includes secure boot, encrypted firmware updates, disabling unused hardware interfaces, access control mechanisms, and using cryptographic authentication for device communication. Additionally, regular vulnerability assessments and penetration testing would help identify and mitigate risks.*  

**Q5: Can you explain how UART, JTAG, and I2C can be exploited in an embedded system, and how you would mitigate these risks?**  
*A5: UART can be exploited to gain root shell access, JTAG allows debugging and full control over the device, and I2C can be used for unauthorized data retrieval. To mitigate these, I would disable or restrict access to these interfaces, use authentication for debugging interfaces, and ensure secure boot is in place to prevent unauthorized firmware modification.*  

#### **Penetration Testing & Reverse Engineering**  
**Q6: How would you perform a penetration test on an embedded device?**  
*A6: I would follow these steps:*  
1. *Identify the attack surface (hardware interfaces, software vulnerabilities, network communication, etc.).*  
2. *Perform firmware analysis using reverse engineering techniques (binwalk, Ghidra, IDA Pro).*  
3. *Test hardware security using JTAG/UART debugging and memory dumping methods.*  
4. *Analyze communication protocols for weaknesses (e.g., sniffing BLE, MQTT security issues).*  
5. *Attempt side-channel attacks or fault injection techniques if applicable.*  
6. *Report findings and suggest mitigation strategies.*  

**Q7: Have you worked with any hardware security assessment tools? If so, which ones?**  
*A7: Yes, I have used tools like JTAGulator for debugging interface enumeration, ChipWhisperer for side-channel analysis, Bus Pirate for communication protocol testing, and SDR tools for RF security analysis. I also use software tools like Ghidra and IDA Pro for firmware analysis.*  

#### **Cryptography & Secure Development**  
**Q8: Can you explain the importance of secure boot and how you would implement it in an embedded system?**  
*A8: Secure boot ensures that only authenticated and signed firmware is executed, preventing unauthorized modifications. It is implemented by storing a cryptographic hash of the firmware in secure storage and verifying it at boot time using a hardware root of trust. If the hash does not match, the boot process is halted to prevent execution of malicious code.*  

**Q9: How do you handle secure firmware updates in IoT devices?**  
*A9: Secure firmware updates should use end-to-end encryption and authentication to prevent tampering. The process includes:*  
- *Digitally signing the firmware image using asymmetric cryptography.*  
- *Verifying the signature before flashing the update.*  
- *Encrypting the firmware during transmission.*  
- *Implementing rollback protection to prevent downgrades to vulnerable versions.*

### **Section 3: Problem-Solving & Scenario-Based Questions (7 minutes)**  

**Q10: Suppose you are assessing a medical IoT device, and you discover an open UART interface that provides root shell access. What steps would you take?**  
*A10: I would immediately report the issue and recommend disabling UART in production firmware. If debugging is required, I would suggest using a secure authentication mechanism. I would also check for other potential attack vectors, enforce access control policies, and ensure that no sensitive data is exposed through UART.*  

**Q11: You have detected an insecure BLE communication issue in a wearable medical device. How would you approach fixing it?**  
*A11: I would analyze the BLE security settings and enforce authentication and encryption (AES-CCM). I would disable unauthenticated pairing modes, ensure secure key exchange mechanisms, and implement device whitelisting to prevent unauthorized connections.*
